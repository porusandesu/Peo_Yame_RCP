# Peo Yame — Storage Monitor

Peo Yame is a Flutter and responsive web prototype for monitoring produce
storage conditions. Both clients display simulated temperature/humidity data,
configured-limit status, trends, and alerts through a Node.js backend. SQLite
persists crop settings, readings, farmer accounts, crop locations and sensor
assignments. The browser dashboard verifies a short-lived PIN generated by the
local server and stores an expiring sign-in token. Until an SMS provider is
connected, the server displays that PIN on screen for local demonstration.
Sensor assignments are saved records; sensor readings remain simulated.

## Start the backend on Windows (no setup)

Download the **peo-yame-backend-windows** artifact from the latest successful
GitHub Actions run and extract the ZIP. Double-click **Peo-Yame-Backend.exe** to
open the dashboard without a server window. To use your phone, connect both
devices to the same Wi-Fi, choose **Connect mobile app** on the dashboard, then
scan its QR code from **Settings** in the phone app. Double-click **Stop Peo
Yame.bat** when you are finished. Your data stays on this computer.

## Start the backend from source

```bash
cd backend
npm install
npm run demo
```

Open `http://localhost:3000` to view the web dashboard, or
`http://localhost:3000/api/status` to inspect the API. In demo mode, the server
binds to loopback and private Wi-Fi interfaces so a phone on the same network
can connect without exposing the listener on public interfaces. Use the
dashboard QR flow instead of sharing the address manually. If the phone cannot
connect, check the firewall and that both devices are on the same network.

## Connect the Android phone

Keep the backend running on the PC and connect the PC and phone to the same
Wi-Fi. In the PC dashboard, open the hamburger menu and choose **Connect mobile
app**. In the mobile app, open **Settings → Monitor connection address**, scan
the QR code, and wait for the connection check before signing in. The backend
address stays hidden in the app settings and is remembered on the phone. Both
clients share farmer accounts and crop assignments when they use this backend;
sign in on each device with the same phone number. The dashboard streams new
readings to the app as they arrive, with periodic refresh as a
fallback. If the PC backend window is closed, the app stays open and shows an
offline message; it reconnects automatically after the backend starts again.

## Build the Android app with GitHub Actions

The **Android build** workflow runs when code is pushed and can also be started
from the repository's **Actions** tab with **Run workflow**. When it finishes,
open the run and download the `storage-monitor-android-debug` artifact. Extract
it and install `app-debug.apk` on an Android device. This is a debug build for
testing, not a Play Store release.

On the web app, choose **Create account**, enter the farmer name and phone
number, then enter the one-time PIN shown by the local server. Returning farmers
can sign in with their saved phone number. In Settings, you can set up Google
Authenticator; after confirming the setup code, future sign-ins use its rotating
6-digit code. The temporary PIN also appears as a
QR code on the web sign-in screen; tap **Scan sign-in QR** in the Flutter app to
authenticate without requesting or typing another PIN. To connect a phone,
open Settings in the mobile app and scan the backend QR code.
Account names and crop locations are stored in the backend database. The mobile
Accounts screen can edit the farmer name, and My Crops can delete a saved crop
location (which also unlinks its sensors). The dashboard breach control remains
a simulation of configured-limit alerts.
Open `http://<PC-IP>:3000` on another device on the same Wi-Fi network.

In **Accounts**, review or edit the farmer profile. In **My Crops**, use **Add
crop and connect sensors** to select a crop, name its field or store, and choose
one or more sensor IDs the backend has received readings from in the past five
minutes. The ID is taken from the sensor reading's `site` field. The page shows
the assigned IDs, and lets you search or delete a location. A location deletion
also unlinks its sensors. The backend does not currently authenticate physical
sensor devices, so this is backend discovery by submitted ID, not verified
hardware identity. SMS delivery still requires a provider integration.

Use the **Harvest** selector to switch between Maize and Tomato. Each selection
loads that crop's illustrative temperature and humidity limits and immediately
adds an in-range simulated reading for the selected crop.

The backend also exposes `/api/health` and sensor-gateway endpoints. To run an
optional simulated sensor that follows the selected harvest, start the backend
first, then run `cd backend && npm run simulate:sensor` in a second terminal.
Sensor readings can be submitted with `POST /api/readings`; recent readings are
available from `GET /api/readings?limit=60`. Alerts can be acknowledged through
`POST /api/alerts/:id/acknowledge`, and incident records use `GET` and `POST`
`/api/incidents`.

## Activity log export

The backend records dashboard and app actions, including harvest changes,
manual refreshes, trend-range changes, alert actions, incident records, sensor
submissions, and demo breaches. The web dashboard's download icon saves a
Markdown file; the Flutter app's export icon opens the device share sheet with
the same file. The API is also available at `GET /api/actions/export.md`.
Entries persist in `backend/data/actions.jsonl` (ignored by Git) and are capped
at the most recent 2,500 actions. Backend startup and export events are logged
too.

## Excel data export

Use the spreadsheet icon in the web dashboard to download `peo-yame-readings.csv`.
The Flutter app offers the same file through the device share sheet. Excel opens
the CSV directly. It includes the latest retained readings, UTC timestamps,
harvest, data source, temperature and humidity, crop limits, and a breach flag.
The export includes the latest 200 readings. Longer chart history remains in
SQLite and is shown as simulated history, separate from live readings.

For a build-time address override, use
`flutter run --dart-define=API_BASE_URL=http://192.168.1.42:3000`.

The audit documents the implementation present in this branch, including
known gaps between the presentation prototype and the research proposal. Crop
limits in the demo are illustrative software settings; they are not validated
spoilage thresholds. The web dashboard reports configured-limit status and
does not estimate crop quality or remaining storage time. Treat any such
heuristics shown in the mobile prototype as illustrative only, never as a
validated prediction.

Use the project only as a controlled local-network demonstration. The backend
uses plain HTTP, OTP delivery is a local demo flow, sessions are in memory, and
the global monitoring and sensor-ingestion APIs are not account-scoped. This is
not ready for exposure to an untrusted network.
